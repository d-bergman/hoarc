# Enable church Gmail delivery

The form and Firebase handler are implemented. Live sending remains disabled until the Gmail credentials, App Check registration and backend deployment are complete. The visible form does not claim delivery is available while those settings are absent. Do not paste a Gmail password or app password into chat, source code or `site.settings.json`.

1. In the church Google account, enable 2-Step Verification and create an app password for website mail. Use an app password, not the account password. If the account does not allow app passwords, an account administrator must resolve that or choose another authenticated sending method.
2. From this checkout, run `npm ci` and `npm --prefix functions ci` if needed, then `npx firebase login`. Run `powershell -File scripts/configure-gmail.ps1` locally. It prompts with hidden input and stores Gmail SMTP configuration and a random rate-limit hashing key in Firebase Secret Manager. It does not deploy anything. This script changes the two named secrets in the `hoarc-a5afd` project only when you explicitly run it.
3. Register the existing web app in Firebase App Check with reCAPTCHA v3, using the authorized domain `d-bergman.github.io`. Register its secret in Firebase’s console and put its public site key in `site.settings.json` as `appCheckSiteKey`. The public site key is safe to commit; the reCAPTCHA secret is not. Do not enable global enforcement for unrelated Firebase products without reviewing their existing clients.
4. In the ignored local `functions/.env.hoarc-a5afd`, set `CONTACT_ENABLED=true` and `ALLOWED_ORIGINS=https://d-bergman.github.io`. CORS origins never include `/hoarc`. Keep the frontend `contactEnabled` setting false until the backend is configured and deployed.
5. Deploy the prepared contact handler, rate-limit cleanup and RTDB rules through the normal approved Firebase launch process. The backend always verifies the App Check signature and exact app ID, checks origin/JSON/body size, validates every field and consent, rejects the honeypot, and limits a hashed IP to five accepted attempts per fifteen minutes. RTDB is used for the private quota, not Firestore. No inquiry is stored as a database record.
6. Set frontend `contactEnabled=true`, build, and publish the website through its existing GitHub Pages process. Its endpoint is `https://us-central1-hoarc-a5afd.cloudfunctions.net/contact`; SMTP credentials never reach the browser. The provider badge and Google notices must remain available; privacy wording covers the contact protection.
7. Send a real approved test from the public site, confirm receipt in `hoarc.church@gmail.com` and spam handling, and use Gmail Reply to confirm it targets the visitor. Confirm that missing/invalid App Check tokens are rejected and that failure messages preserve the typed inquiry. Turn sending off again if any check fails.

Mail uses church Gmail as the authenticated From address, a fixed church recipient and the visitor as Reply-To. First name, last name and email are required in both browser and server validation; the existing subject/message and consent fields are also required. No real test email or Firebase deployment was performed during this implementation.

References: [Firebase web App Check setup](https://firebase.google.com/docs/app-check/web/recaptcha-provider), [server-side token verification](https://firebase.google.com/docs/app-check/custom-resource-backend), [Google app passwords](https://support.google.com/accounts/answer/185833).
